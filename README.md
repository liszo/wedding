# دعوت‌نامه‌ی عروسی — شقایق و رامین

A private, per-guest Persian wedding invitation. Every guest gets their own link, is
greeted by name, RSVPs once, and can post to a shared wall.

Next.js 16 (App Router) · Tailwind v4 · Supabase · Motion.

```bash
npm run dev      # http://localhost:3000
npm run assets   # regenerate public/design from design/ (only after changing artwork)
npm run build
npm run lint
```

## Where things live

| Path | What |
|---|---|
| `content/config.ts` | **Edit this first.** Names, dates, venue (including the Neshan place link), running order. Everything user-facing reads from it. |
| `content/story.ts` | The three chapters: خواستگاری → بله‌برون → عروسی. Date and title only. |
| `content/photos.generated.ts` | Generated by `npm run assets` — do not hand-edit. |
| `design/` | The artwork library. `design/ASSETS.md` documents every file and the rules for using it. |
| `scripts/prepare-assets.ts` | Crops, tones and compresses the photographs; shrinks the stickers; writes the manifest. |
| `scripts/tokens.ts`, `scripts/seed-guests.ts` | Guest list and invite-link generation. |

## Visual system (current: nude minimal)

White, sand and warm umber. Almost everything — the seams, the card border, the
envelope, every hairline — is drawn in CSS. Exactly **two ornaments** are served, both
re-tinted from their gold masters to the palette at build time: a braided rule under
section headings, and a lily crown as the footer mark. Nothing else from the library
ships.

Below the photograph the whole page sits inside `.card-body`, which draws one
continuous ruled border down its full length — the engraved rule a printed invitation
carries. Bands alternate white and nude, and each `<Seam>` divides them with a hairline
broken by a small diamond. The break is deliberate: an unbroken line through a filled
diamond would need the diamond to know which band it sits on.

Tokens are defined once at the top of `app/globals.css` with their contrast ratios
against both grounds. `--taupe` and `--line` are hairlines and are never used for text.

| Piece | What it does |
|---|---|
| `<Band tone>` | a section; alternates `white` and `nude` grounds, 74px of vertical padding, 34px of side margin |
| `<SectionHead>` | optional label → nastaliq title → ornament rule |
| `<Rule>` | a 46px centred hairline, between blocks of one section |
| `<Seam tone>` | the division between two bands; carries the ground of the band above it |
| `.loading-bar` | the عروسی chapter's crawl — see below |

The content
column (roughly 300px inside a 430px card) is much narrower than the card itself; those
wide margins are most of what makes it read as printed rather than as a web page.

**Photographs are duotone.** `scripts/prepare-assets.ts` maps every image through one
warm three-stop curve (`#4A423C` → `#C9B8AC` → `#FAF7F3`) so the whole site reads as a
single material. A flat `sharp.tint()` cannot do this — it scales toward one colour and
leaves midtones neutral, which reads as grey-with-a-cast. The midtone stop is the point:
it is where skin sits.

**The wedding chapter never finishes loading.** It has no photograph and no text because
it has not happened yet, so it renders a crawling progress bar and «به‌زودی…» whose dots
never resolve.

The hero anchors its type with `left`, not `start`. The page is RTL, so the logical
property would put the names in the opposite corner from the empty wall they are meant
to sit on.

Two directions preceded this one and are in the git history: an ivory *tazhib* build
(lapis and Persian illumination) and a botanical one (olive bands, domes, scalloped
hems, floral seams). Both are gone from the code. If you ever want them back, the
ornament library they used is still complete under `design/`.

## Opening sequence

Two overlays, in order, both session-scoped so they appear once per visit:

1. **`<MusicGate>`** asks whether to play the soundtrack. It has to come first —
   browsers only allow `play()` during a user gesture, so `lib/music.ts` keeps the
   `<audio>` element in a module-level store and the gate calls `choose("yes")` straight
   from its own click handler, while that gesture still counts. The 4.7MB track is
   `preload="none"` until someone says yes.
2. **`<Envelope>`** — the sealed gate, drawn in CSS: a paper envelope whose flap swings
   back in 3D, sealed with a hairline ring holding the two initials. It waits for a
   music answer before rendering, so the two never stack or fight over focus.

## Guest flow

1. `scripts/tokens.ts` writes `guest-links.csv` — one `/i/<token>` URL per guest.
2. `/i/[token]` verifies the token, sets an HMAC-signed session cookie, redirects home.
   A bad or rate-limited token redirects with `?e=bad` / `?e=slow`, which `LinkNotice`
   renders as an explanation rather than a silent drop.
3. `/api/lookup` is the recovery path — a guest who lost their link enters their phone
   number and gets the session back.
4. `/admin` (password) shows every response and exports CSV.

## Maps

`wedding.venue.neshan` holds Neshan's **saved-place** short link. A `/maps/@lat,lng,zoom`
URL only points the camera at a spot and renders no marker, so a guest arrives at an
unlabelled patch of map. Only `places/<id>` (and its `nshn.ir` short form) drops the pin.
`lat`/`lng` are still used for the Google Maps link and the `GEO:` line in the .ics.

Both `guests.csv` and `guest-links.csv` are gitignored. They contain real phone numbers.

## Images

Nothing goes through `next/image`. Every image is a static WebP that `npm run assets`
already cropped and compressed to its display size, with `width`/`height` set at the
call site so nothing reflows — the whole served set is under 900KB, and thumbnails are what the page actually loads. Guest
uploads on the wall are compressed in the browser (`lib/compress.ts`) before upload.
The `@next/next/no-img-element` rule is switched off in `eslint.config.mjs` for exactly
this reason.

## Environment

```
SUPABASE_URL=
SUPABASE_SERVICE_ROLE_KEY=
SESSION_SECRET=            # any long random string; signs the guest cookie
ADMIN_PASSWORD=
NEXT_PUBLIC_SITE_URL=      # optional; only needed if not deploying on Vercel
```

`NEXT_PUBLIC_SITE_URL` sets `metadataBase`, which is what makes the WhatsApp/Telegram
link preview resolve its image. On Vercel it is inferred from
`VERCEL_PROJECT_PRODUCTION_URL`.
